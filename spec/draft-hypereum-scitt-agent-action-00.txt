      SCITT Agent Action Receipts and Transparent Capsule Profile
                  draft-hypereum-scitt-agent-action-00

Abstract

   This document specifies the Agent Action Capsule profile
   ("urn:hivemind:receipts:capsule:1") for Supply Chain Integrity,
   Transparency, and Trust (SCITT) Signed Statements and portable ".hvr"
   ("application/vnd.hivemind.receipt+cose") bundles.  It defines a
   deterministic CBOR and JSON Canonicalization Scheme (JCS) dual-digest
   payload format, COSE_Sign1 envelope profiling, algorithm policy
   separating transparency service keys from customer issuer keys,
   privacy-preserving off-log salted commitments with envelope key
   destruction (crypto-shredding), Merkle inclusion receipts anchored in
   signed-note checkpoints with a witness cosignature quorum, and long-
   term archive preservation via Evidence Record Syntax (ERS) with
   cryptographic timestamps.

1.  Introduction

   Autonomous AI agents invoke tools, Model Context Protocol (MCP)
   endpoints, Agent-to-Agent (A2A) tasks, and external HTTP APIs on
   behalf of human and workload principals.  Conventional telemetry logs
   are mutable, omit denied or failed attempts (survivorship bias),
   conflate attempted tool calls with confirmed side effects, and leak
   sensitive personal data or prompt arguments into append-only storage.

   This specification profiles the IETF SCITT architecture
   [I-D.ietf-scitt-architecture] and SCITT Reference APIs (SCRAPI)
   [I-D.ietf-scitt-scrapi] to provide cryptographically verifiable,
   offline-auditable receipts for every agent action decision and
   execution outcome.

3.  Relationship to Other SCITT Agent Specifications

   Two related individual submissions in the SCITT Working Group address
   adjacent aspects of AI agent transparency.  This section clarifies
   how "draft-hypereum-scitt-agent-action" complements and extends both
   specifications.

3.1.  Relationship to draft-mih-scitt-agent-action-capsule

   The individual draft [I-D.mih-scitt-agent-action-capsule] introduces
   the problem statement and conceptual data model for recording
   discrete agent actions as SCITT Signed Statements.  This
   specification builds upon that conceptual framing and provides the
   normative wire-format and verification rules required for
   interoperable implementation:

   *  Exact deterministic CBOR [RFC8949] Section 4.2 and JCS [RFC8785]
      dual canonical digest rules ("capsule_id") with byte-for-byte test
      vectors;

   *  Four formally verified protocol invariants (Completeness across
      all six verdict classes, Confirmed Effect Binding, Anchored Ledger
      Claim verification, and Class-1 Offline Determinism);

   *  A salted HMAC-SHA-256 commitment construction paired with KMS
      envelope key destruction (crypto-shredding) and optional BBS
      selective disclosure [RFC9380] so sensitive prompts and arguments
      never enter the append-only Merkle log;

   *  Binding of [RFC9162] inclusion proofs inside COSE receipts
      [RFC9942] to C2SP signed-note checkpoints cosigned by a witness
      quorum.

3.2.  Relationship to draft-emirdag-scitt-ai-agent-execution

   The individual draft [I-D.emirdag-scitt-ai-agent-execution] focuses
   on high-level AI agent execution provenance, model invocation
   telemetry, and runtime workload identity attestation.  By contrast,
   this specification operates at the per-action authorization and side-
   effect boundary:

   *  Whereas [I-D.emirdag-scitt-ai-agent-execution] attests that an
      agent runtime executed a workflow, this profile records each
      individual MCP, A2A, HTTP, or tool call together with its policy
      disposition ("executed", "blocked", "denied", "errored",
      "engine_failure", or "timed_out") and the cryptographic digest of
      the observed side effect;

   *  Hardware and runtime attestation evidence defined in
      [I-D.emirdag-scitt-ai-agent-execution] can be referenced directly
      inside the "runtime.attestation_ref" and
      "assurance.attestation_mode" fields of an Agent Action Capsule,
      allowing implementers to combine runtime execution provenance with
      per-action SCITT receipts.

4.  Agent Action Capsule Format and Invariants

4.1.  Binding Protocol Invariants

   Every implementation conforming to profile
   "urn:hivemind:receipts:capsule:1" MUST enforce four binding
   invariants:

   1.  *No Survivorship Bias (Completeness)*: A signed capsule MUST be
       emitted for every verdict class: "executed", "blocked", "denied",
       "errored", "engine_failure", and "timed_out".

   2.  *Confirmed Effect Binding*: A capsule with "effect.status" equal
       to "confirmed" MUST have "verdict_class" equal to "executed" and
       MUST carry a non-empty "effect.response_digest" computed over the
       observed response.

   3.  *Anchored Ledger Claim*: A capsule claiming
       "assurance.ledger_mode" equal to "anchored" MUST be rejected by
       verifiers unless accompanied by a verified [RFC9162] inclusion
       receipt [RFC9942] anchored in a log-signed and witness-quorum-
       cosigned checkpoint.

   4.  *Offline Class-1 Verification*: Class-1 verification MUST be
       deterministic and completely offline, consulting no external
       network, no AI model, and no heuristic wall-clock skew

       assumptions.  Each verification run MUST bind its deterministic
       run identifier to the verifier build digest, statement bytes,
       checkpoint text, and canonical trust roots.

4.2.  Dual Canonical Digests (CBOR and JCS)

   The canonical identifier "capsule_id" MUST be computed as
   "sha256:<hex>" over the [RFC8949] Section 4.2 Core Deterministic
   Encoding CBOR bytes of the CapsuleCore map (excluding "capsule_id").
   Implementations SHOULD also compute a JSON canonical digest as
   "sha256:<hex>" over the UTF-8 bytes of the [RFC8785] JSON
   Canonicalization Scheme (JCS) serialization of the CapsuleCore
   object.

5.  SCITT Envelope, Transparency Log, and Algorithm Profile

5.1.  COSE_Sign1 Statement and CWT Claims

   An Agent Action Capsule is carried as the payload of a tagged
   COSE_Sign1 (CBOR Tag 18, [RFC9052]) envelope:

   *  Protected header parameter 1 ("alg"): keys operated by the
      Transparency Service operator (log checkpoint and receipt keys,
      and operator-hosted statement issuer keys) MUST use EdDSA (-8).
      Statements submitted by external customer issuers MAY use EdDSA
      (-8), ES256 (-7), or ES384 (-35) when registered in the verifier's
      trust store.

   *  Protected header parameter 3 ("content_type") MUST be
      "application/vnd.hivemind.agent-action-capsule+cbor" (or
      "application/vnd.hivemind.receipt+cose" at the bundle transport
      layer).

   *  Protected header parameter 4 ("kid") MUST identify the issuer key,
      RECOMMENDED to be the base64url-encoded [RFC9679] COSE Key
      Thumbprint.

   *  Protected header parameter 15 ("cwt_claims", [RFC9597]) SHOULD
      carry CWT claims 1 ("iss"), 2 ("sub"), and 6 ("iat").

5.2.  Post-Quantum Countersignatures (ML-DSA-65)

   Statements MAY carry a post-quantum ML-DSA-65 [FIPS204] [RFC9964]
   countersignature in unprotected header parameter 7 (or -25900) using
   algorithm -49 when enabled by relying-party policy.

5.3.  RFC 9162 Inclusion Proofs and Witness Quorum

   Transparency log receipts ("application/scitt-receipt+cose") are
   attached in unprotected header parameter 394 ("receipts") per
   [RFC9942], with protected parameter 395 ("vds" = 1 for [RFC9162]
   SHA-256 Merkle trees) and unprotected parameter 396 ("vdp" containing
   the bstr-wrapped CBOR inclusion proof "[tree_size, leaf_index, [*
   sha256_hash]]").  Checkpoints MUST be verified against both the log's
   Ed25519 note key (type 0x01) and a configured witness cosignature
   quorum (type 0x04).

5.4.  Long-Term Archive Evidence Records (RFC 4998 and RFC 3161)

   Archives requiring multi-year non-repudiation across cryptographic
   algorithm transitions MAY encapsulate checkpoint or batch Merkle
   roots inside ASN.1 DER EvidenceRecord structures [RFC4998] stamped
   with [RFC3161] CMS TimeStampTokens.

6.  Selective Disclosure and Privacy Architecture

   Sensitive fields ("principal.subject", "operation.target", "request",
   "response", "effect.summary") MUST NOT appear in cleartext in a
   logged capsule.  Each field enters the capsule as "HMAC-SHA-
   256(salt_32, field_name || 0x00 || det_cbor(value))" where
   "privacy.salt_commitment = sha256(salt_32)".  When a holder must
   disclose a subset of attributes without cross-presentation
   correlation, issuers MAY accompany the capsule with a BBS proof over
   BLS12-381 [RFC9380].

8.  Security Considerations

   Enforcing a witness cosignature quorum with intersection at least one
   honest witness prevents undetected split-view equivocation by the
   Transparency Service.  Separating the KMS signing key of the
   Transparency Service from the KMS signing key of the statement issuer
   ensures that compromise of an issuer role cannot forge log inclusion
   receipts or checkpoints, and vice versa.  All verifiers MUST reject
   non-deterministic CBOR encodings (indefinite lengths, duplicate or
   unsorted map keys, or invalid UTF-8 text strings) before evaluating
   cryptographic signatures.

9.  Privacy Considerations

   Storing only 256-bit salted HMAC commitments on the Merkle log
   prevents dictionary and rainbow-table attacks on low-entropy
   attributes.  Wrapping the off-log 32-byte salt under a per-subject or
   per-workspace Data Encryption Key (DEK) enables erasure by key
   destruction (crypto-shredding) without invalidating the Merkle tree.
   Public transparency logs MUST NOT record customer workspace
   identifiers, user email addresses, agent names, or tool arguments.

10.  IANA Considerations

   IANA is requested to register the media types "application/
   vnd.hivemind.receipt+cose" (file extension ".hvr") and "application/
   vnd.hivemind.agent-action-capsule+cbor" in the "Media Types"
   registry.
